# ADR-0011: Nova Post delivery-point picker

Status: **Proposed**. Written after a spike and **revised after a lead decision** (below). This record authorizes no paid service, no carrier account, no secret provisioning and no notification. Open lead decisions are in [Lead decisions](#lead-decisions); their defaults apply until the lead answers. It does not decide ADR-0007 Q1.

Numbering: the orchestrator assigned 0011. Number 0010 was claimed by a branch that never merged. The orchestrator confirms this number and migration `0012` at integration.

Contract sources, in order of precedence: this record, then [docs/API.md](../API.md#nova-poshta-delivery-points-adr-0011). This record partly supersedes [ADR-0003](0003-client-accounts.md) (Nova Poshta preference) and [ADR-0007](0007-customer-cart-checkout.md) (checkout body and snapshot); see [Supersession](#supersession).

## Lead decision and simplification

The lead decided (relayed): **"we only need api to get branches list, no deep integration; see https://github.com/PerspectiveTeam/NovaposhtaCatalog; we dont have business account".** Consequences for this record:

- **L1 is decided: no API key.** All calls are keyless. The sync script still sends `apiKey` if the environment variable `NOVA_POSHTA_API_KEY` is set, so a key can be added later without code changes. Nobody requests or provisions one.
- **Pattern adopted from PerspectiveTeam/NovaposhtaCatalog** (MIT Magento 2 module): a scheduled sync copies Nova Poshta's directory into local storage, and checkout reads only the local copy. The module itself is PHP for Magento and is not reused. Its sync-safety idea is adopted in a simpler form: a sync that loses more than 20% of the points of the current snapshot is rejected.
- **Removed from the first draft:** the live Worker proxy and every per-request upstream call; cold-listing budgets and in-flight coalescing; checkout-time upstream verification; the `np-api`/`manual` verification distinction with its upgrade and downgrade guard; the `WarehouseId` fallback; redirect handling in the Worker; the lookup throttle; the Cache API; free-text manual points.
- **Why this is better here.** The catalog is small once reduced (about 13 MB, measured below) and changes slowly. Serving it from our own storage makes picker latency and availability independent of Nova Poshta, removes all upstream traffic from customer requests, and lets the Worker run within the **Workers Free** limits (10 ms CPU, 50 external subrequests), which the first draft could not.

## Context

- **Request.** Customers choose a city, then a branch (відділення) or a parcel locker (поштомат). The form appears at checkout and in the cabinet. The cabinet holds a favourite point. If none is set, the point from the latest order is remembered. A signed-in customer gets the favourite (or remembered point) prefilled at checkout and may override it for one order.
- **Current state.** `customer_profiles` (`migrations/0006_customer_profile.sql`) has `np_type`, `np_city_name`, `np_city_ref`, `np_warehouse_number`, `np_warehouse_ref`, `np_note` and `np_source` (`manual`|`np-api`). `apps/api/src/customer-profile.js` validates a free-text preference and stores `source:"manual"`. No code calls Nova Poshta. The cabinet (`apps/web/src/account/Account.jsx`) shows only a placeholder for contacts, Telegram and delivery; `apps/web/src/account/account-api.js` has no profile client.
- **Checkout.** `POST /api/cart/checkout` (ADR-0007) accepts only `{lines}`, binds the cart to a valid customer session and stores an immutable snapshot (`migrations/0011_carts.sql`). ADR-0007 rejected a contact or delivery form at checkout because it would collect personal data from anonymous visitors. Anonymous checkout must keep working.
- **Staff boundary.** Staff cart responses expose only `bound:boolean`. ADR-0007 Q1 is open. *(Answered yes in the ADR-0007 completion amendment: see §9.)*
- **Storage and runtime.** The Worker has an optional R2 binding `MEDIA`, generated by `tools/cloudflare-config.mjs` from `CLOUDFLARE_R2_BUCKET` (production) and `STAGING_R2_BUCKET` (`storefront-skeleton-media-staging`). Dedicated snapshot buckets are now provisioned and bound as `NP_CATALOG` from `NP_CATALOG_BUCKET` (`storefront-skeleton-np-catalog`) and `STAGING_NP_CATALOG_BUCKET` (`storefront-skeleton-np-catalog-staging`, exported as `STAGING_NP_CATALOG_BUCKET_NAME`); each must differ from its media bucket and staging from production. When the variables are unset no `NP_CATALOG` binding is generated and the Worker falls back to `MEDIA`, a local and dev fallback only. `serveMedia` (`apps/api/src/index.js`) serves only keys matching `^[a-f0-9-]+\.(jpg|png|webp)$`; the cutout code (`apps/api/src/image-processing.js`) applies a similar key pattern. Keys under another prefix are therefore not reachable through `/media/`, but only incidentally: a T3 test pins it (§4). Production has one Worker cron (`*/5 * * * *`, supplier sync); staging has none. GitHub Actions already hold `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` and `STAGING_CLOUDFLARE_API_TOKEN` for deploys. `tools/stockify.mjs` (on staging) is a precedent for a local script that writes to R2 through the Cloudflare REST API.
- **Security headers.** The Worker sets `X-Content-Type-Options`, `Referrer-Policy` and `X-Frame-Options`. There is **no CSP and no `Permissions-Policy`**, so same-origin geolocation is allowed by default.
- **Earlier references.** ADR-0003 planned a Nova Poshta lookup cache. That task was never created; this record replaces it.

## Decision

### 1. Approach

- **Sync script** `tools/np-catalog-sync.mjs` (Node 22, no dependencies): pulls all points keyless, reduces and shards them, and uploads a new snapshot to R2 through the Cloudflare REST API. `--out <dir>` writes the same layout to a local directory without credentials (tests, review and QA).
- **Pure helpers** in `packages/catalog/delivery.js`: classification, normalization, the point shape, shard keys, city search matching and input validation. Shared by the script and the Worker, testable in Node.
- **Worker** `apps/api/src/nova-poshta.js`: two `GET` endpoints that read only our snapshot, plus `resolvePoint(env, warehouseRef)` for the profile and checkout writes. **The Worker never calls Nova Poshta.**
- **Frontend** `apps/web/src/delivery/NovaPoshtaPicker.jsx`, used by the cart page and the cabinet.
- **No new runtime dependency.** `package.json` changes only in its scripts.

### 2. Snapshot format

All keys are under `np-catalog/v1/` in the bucket (`NP_CATALOG ?? MEDIA`). `<sid>` is the snapshot ID, the UTC generation time as `YYYYMMDDTHHMMSSZ`.

| Key | Content |
| --- | --- |
| `current.json` | Manifest `{version:1, snapshotId, generatedAt, points, branches, postomats, cities, cityLetters:[...], source:"api.novaposhta.ua/v2.0 Address.getWarehouses"}`. `snapshotId` matches `^\d{8}T\d{6}Z$`. `branches` and `postomats` are the per-kind point counts. `cityLetters` is required and lists exactly the city-shard letters written. **Written last**; switching it publishes a snapshot. |
| `<sid>/cities/<letter>.json` | City shard: all cities whose normalized name starts with that letter, as `[{ref, name, area, branches, postomats}]`. `<letter>` is the first character of the lowercased name; the key segment is `encodeURIComponent(letter)`, stored literally (for example `%D0%BA`). Written only for letters in `cityLetters`. |
| `<sid>/points/<h>.json` | Point pack for cities whose `cityRef` starts with hex digit `<h>` (all 16 packs are always written, empty ones as zero bytes): concatenated UTF-8 JSON slices, one per city and kind, each a complete `{cityRef, kind, generatedAt, items:[NpPoint]}`. |
| `<sid>/points/<h>.idx.json` | `{cityRef: {branch:[offset,length], postomat:[offset,length]}}` byte ranges into the pack; all 16 are always written (`{}` when empty). |
| `<sid>/refs/<hh>.json` | Ref shard for points whose `Ref` starts with `<hh>`: `{ref: {cityRef, cityName, kind, number, name}}`; all 256 are always written (`{}` when empty). |

- **Point shape.** `NpPoint = {ref, number:string|null, name, lat:number|null, lon:number|null}`. `name` is Nova Poshta's `Description` (contains the address, at most 200 code points). `kind` is per slice, not per point.
- **Classification (allowlist).** `CategoryOfWarehouse` `Postomat` → `postomat`; `Branch` or `Store` → `branch`. Every other value (`DropOff`, `Fulfillment`, `OtherOperating`, unknown, missing) is excluded. Only `WarehouseStatus === "Working"` and `DenyToSelect !== "1"` are kept. Records with an invalid `Ref` or `CityRef` are dropped; duplicates by `Ref` are dropped.
- **Text.** NFC; control characters (`\p{Cc}`: C0, DEL and C1) become a space and format characters (`\p{Cf}`) are removed; collapse whitespace; trim; apostrophe variants → `ʼ` (U+02BC). City `name` is `CityDescription` (already disambiguated by Nova Poshta), `area` is `SettlementAreaDescription`. Records whose city name or point name is empty after normalization are dropped.
- **Number.** Kept if it matches `^[0-9]{1,6}$`, else `null`.
- **Coordinates.** Kept, because they cost only 12% of the raw size: `Number(lat)`/`Number(lon)` rounded to 5 decimals; if either value is non-finite, zero, or outside latitude 44–53 and longitude 22–41, **both** become `null` (coordinates are nulled as a pair).
- **Ordering.** Points by numeric `number` (`null` last), then `ref`. Cities in a shard by `branches + postomats` descending, then name.

### 3. Sync script (`tools/np-catalog-sync.mjs`)

- **Pull.** `POST https://api.novaposhta.ua/v2.0/json/` `{modelName:"Address", calledMethod:"getWarehouses", methodProperties:{Limit:"500", Page, Language:"UA"}}`, plus `apiKey` only when `NOVA_POSHTA_API_KEY` is set. Page 1 gives `info.totalCount`; the remaining pages run with at most **2 concurrent** requests, 30 s timeout per request, up to 3 attempts with backoff. Responses must be JSON with `success:true` and a `data` array; redirects are not followed.
- **Completeness and safety (from the reference module).** The script first reads the current `current.json`:
  - **404**: first run; there is no previous snapshot and the drop guard does not apply.
  - **Any other read or parse error**, or a manifest that fails the §4 checks (which include `points` being a non-negative integer and `cityLetters` an array): abort (exit 1) without uploading anything. Exception: a local `--force` run treats an invalid manifest as missing (no previous snapshot, no drop guard).
  - Otherwise its `snapshotId` is **the previous snapshot**, its `points` the total baseline, and its `branches`/`postomats` the per-kind baselines. A previous manifest without per-kind counts (older format) gets only the total check.

  The sync then aborts **without publishing** (exit 1, with a one-line summary of the reason and counts) when: any page fails after retries; fewer records than `totalCount` were received, except a shortfall of at most max(10, 0.1% of `totalCount`) when every page before the last was full and the last page came back short (Nova Poshta's reported count can run slightly higher than the records it returns); no points remain; or the kept points are fewer than **80%** of the baseline (the reference module's 20% rule). The 80% check also applies per kind (`branch` and `postomat` separately) when the previous manifest has per-kind counts, so losing one kind is caught. A sync whose new `snapshotId` equals the previous one is also refused. **Recovery:** after checking that the drop is real, a person runs the script locally with `--force`, which skips only the 80% checks. The workflow has no force input.
- **Transports.** Two, chosen by configuration:
  - **S3 API (automation and preferred):** the R2 S3-compatible endpoint `https://<CLOUDFLARE_ACCOUNT_ID>.r2.cloudflarestorage.com/<bucket>` with SigV4 signing implemented in the script (`node:crypto`, no dependency), using an access key pair scoped to the one bucket. `PutObject`, `ListObjectsV2` and `DeleteObject`. Not subject to the Cloudflare REST API rate limit.
  - **REST API (local runs only):** `PUT/GET/DELETE /accounts/{CLOUDFLARE_ACCOUNT_ID}/r2/buckets/{bucket}/objects/{key}` and the bucket's object listing (the backend task confirms the list endpoint and its pagination) with a person's `CLOUDFLARE_API_TOKEN`, like `tools/stockify.mjs`. About 320 uploads plus at most about 320 deletions per run fit the 1,200 requests per 5 minutes limit at 4 in flight. **Never used when `GITHUB_ACTIONS=true`**: in Actions the script accepts only the dedicated S3 credentials and ignores `CLOUDFLARE_API_TOKEN` even if present.
- **Upload.** At most 4 in flight, `Content-Type: application/json; charset=utf-8`. All `<sid>/` objects first, then `current.json`.
- **Retention and deletion.** After publishing, list `prefix=np-catalog/v1/` and delete only keys that match `^np-catalog/v1/(\d{8}T\d{6}Z)/` whose captured snapshot ID is **neither the new one nor the previous one** (the `snapshotId` read from a valid `current.json` before publishing). Keys outside that pattern, including `current.json`, any other prefix and every product photo in a shared bucket, are never deleted. When a valid previous manifest exists, an orphan prefix from an aborted run that is older than 10 minutes is deleted by the next successful run, and can never displace the previous snapshot, because "previous" comes from the manifest, not from listing order. If publishing failed, nothing is deleted. Snapshot prefixes younger than **10 minutes** (by their snapshot ID) are never deleted, so a concurrent run's upload in progress survives. When the previous snapshot is unknown (first run, or a local `--force` run over an invalid manifest), **nothing is deleted**.
- **Configuration** (environment only; never read from `.dev.vars` or another checkout; values never logged):
  - `CLOUDFLARE_ACCOUNT_ID`.
  - S3 transport: `NP_CATALOG_R2_ACCESS_KEY_ID`, `NP_CATALOG_R2_SECRET_ACCESS_KEY`.
  - REST transport (local only): `CLOUDFLARE_API_TOKEN`.
  - `NP_CATALOG_BUCKET`; if unset, `--staging` defaults to `storefront-skeleton-np-catalog-staging`. There is no default to `CLOUDFLARE_R2_BUCKET`: a sync never writes into the photo bucket unless that bucket is explicitly named. The workflow reads only `vars.NP_CATALOG_BUCKET` and `vars.STAGING_NP_CATALOG_BUCKET`, with no media-bucket fallback, and skips with a notice when the variable is missing.
  - Optional `NOVA_POSHTA_API_KEY` (never set under L1).
- **Output.** A summary line: snapshot ID, pages, upstream MB, points, cities, objects, uploaded MB, durations. No upstream bodies and no token in logs or errors.
- **Workflow `.github/workflows/np-catalog.yml`.**
  - Triggers: **only** `schedule` (`30 0 * * *` UTC, 02:30/03:30 Kyiv) and `workflow_dispatch`. No `push`, `pull_request` or `pull_request_target`.
  - Every job has `if: github.ref == 'refs/heads/main'` (precedent: the branch gate in `staging.yml`), `permissions: contents: read`, `timeout-minutes: 15` and `concurrency: {group: np-catalog-<env>, cancel-in-progress: false}`.
  - Two jobs, `production` and `staging`. Secrets: `CLOUDFLARE_ACCOUNT_ID` (existing), `NP_CATALOG_R2_ACCESS_KEY_ID` and `NP_CATALOG_R2_SECRET_ACCESS_KEY` (production), `STAGING_NP_CATALOG_R2_ACCESS_KEY_ID` and `STAGING_NP_CATALOG_R2_SECRET_ACCESS_KEY` (staging). Bucket names come from repository variables (`NP_CATALOG_BUCKET`/`STAGING_NP_CATALOG_BUCKET`, falling back to `CLOUDFLARE_R2_BUCKET`/`STAGING_R2_BUCKET`). The deploy tokens (`CLOUDFLARE_API_TOKEN`, `STAGING_CLOUDFLARE_API_TOKEN`) are **never** referenced.
  - The skip check looks only at the job's two dedicated secrets: if either is empty, the job writes a notice to the step summary and exits 0, so the workflow is safe to merge before L6.
  - Third-party actions (`actions/checkout`, `actions/setup-node`) are pinned by full commit SHA. No `set -x`, no printing of environment variables; secrets are passed only through `env:` of the single script step.
  - Until L6, a person runs `npm run np:sync` locally (default (b)).
- **Freshness.** Nova Poshta recommends a nightly refresh. A snapshot older than **7 days** is still served (stale data beats none); `generatedAt` is returned to clients and QA checks it. See revisit triggers.

### 4. Read endpoints

- **Mount.** `/api/delivery` and `/api/delivery/*` are dispatched at the **top of `route()` in `index.js`, before `loadRecognition(env)` and before the `env.DB` check** (both currently run for every `/api/*` path except `/api/health`), and therefore also before the global `checkOrigin`. The endpoints need no D1: they work when `env.DB` is absent or failing. Other methods get this handler's `405`. Only `GET`. No session, no cookies. **No throttle**: requests touch no D1 and no upstream.
- **Headers.** `200` responses: `Cache-Control: public, max-age=300`. Error responses (`400`, `404`, `405`, `503`): `Cache-Control: no-store`. All: `X-Robots-Tag: noindex`, `Content-Type: application/json; charset=utf-8`. `/api/delivery` is **not** added to `PRIVATE_PREFIXES` (that would force `no-store` on public reference data).
- **Manifest.** Read once per isolate and cached in memory for 60 s. It is usable only if it parses, `version === 1`, `snapshotId` matches `^\d{8}T\d{6}Z$`, `cityLetters` is an array and `points` is a non-negative integer; otherwise, or with no bucket binding or no manifest, → `503 {error:"catalog_unavailable"}`.
- **Objects.** Every object the manifest implies (the 16 packs and indexes, the 256 Ref shards, and the city shards for letters in `cityLetters`) must exist; a missing one → `503 catalog_unavailable`. A query letter **not** in `cityLetters` → `200` with empty `items` (no read).
- **Lookups.** Index and shard lookups use `Object.hasOwn`, so keys like `__proto__` never match.
- **Processing order.** Unknown path → `404 {error:"not_found"}`. Other method → `405 {error:"method_not_allowed"}` with `Allow: GET`. Query → `400 {error:"invalid_request"}`. Snapshot → `503 {error:"catalog_unavailable"}`.
- **`GET /api/delivery/np/cities?q=`**
  - `q` is required and is the only parameter: NFC, trim, collapse whitespace, apostrophe variants → `ʼ`, lowercase; then 2–50 characters of letters, digits, spaces and `ʼ-.,()`. Otherwise `400`.
  - The Worker reads the shard for the first character of `q`, keeps cities whose lowercased `name` starts with `q`, and returns at most 20: exact name matches first, then the shard order (bigger cities first).
  - Response: `{generatedAt, items: CityOption[]}` with `CityOption = {ref, name, area, branches, postomats}`. A letter without a shard → empty `items`.
- **`GET /api/delivery/np/warehouses?cityRef=&kind=`**
  - `cityRef` and `kind` (`branch`|`postomat`) are required, and no other parameter is allowed. `cityRef` is lowercased first, then must match the lowercase GUID pattern (so uppercase input is accepted and normalized).
  - The Worker reads `points/<h>.idx.json`, then calls `bucket.get(packKey, {range:{offset, length}})` and streams the body **without parsing it**. A missing pack, a returned range whose offset or length differs from the request, or an object `size` that is not a safe integer ≥ `offset + length` → `503 catalog_unavailable`. The body is exactly `{cityRef, kind, generatedAt, items: NpPoint[]}`.
  - A city or kind absent from the index → `200` with the same shape and empty `items` (generated by the Worker).
  - Size: Kyiv postomats are the largest response, 1.81 MB raw and 276 KB gzipped.
- **`resolvePoint(env, warehouseRef)`** (internal): reads `refs/<hh>.json` and returns `{cityRef, cityName, kind, number, name}` or `null`. It throws `catalog_unavailable` when the snapshot cannot be read.
- **Logging.** Application logs record only the error class (`catalog_unavailable`, `invalid_request`). They never contain query text, Refs or coordinates. Platform request logs (Workers observability is enabled) may record request URLs, which contain `q` and `cityRef` but never coordinates or customer identity.

### 5. Data model (`migrations/0012_delivery_point.sql`)

Additive columns only.

```sql
ALTER TABLE customer_profiles ADD COLUMN np_warehouse_name TEXT;
ALTER TABLE customer_profiles ADD COLUMN np_origin TEXT CHECK (np_origin IS NULL OR np_origin IN ('cabinet','checkout'));
ALTER TABLE carts ADD COLUMN dp_type TEXT CHECK (dp_type IS NULL OR dp_type IN ('branch','postomat'));
ALTER TABLE carts ADD COLUMN dp_city_name TEXT;
ALTER TABLE carts ADD COLUMN dp_city_ref TEXT;
ALTER TABLE carts ADD COLUMN dp_warehouse_number TEXT;
ALTER TABLE carts ADD COLUMN dp_warehouse_ref TEXT;
ALTER TABLE carts ADD COLUMN dp_warehouse_name TEXT;
```

- **A stored point = the Ref plus a display snapshot** (type, city name, city Ref, number, name) copied from the catalog at write time. If the Ref later disappears from the catalog, the stored snapshot is still shown.
- `dp_type IS NULL` means "no delivery point"; all `dp_*` are then `NULL` (enforced by the API). `dp_*` are snapshot columns, written only at insert and cleared only on account deletion (§9).
- **Legacy rows.** No code before this record wrote `np-api`; ADR-0003's `PATCH` stores client-supplied values, **including client-supplied Refs**, with `np_source='manual'`. So a **legacy preference is any row with `np_source='manual'`, with or without a `warehouseRef`**. The migration leaves its `np_origin` `NULL`. `np_source` is kept: every new write sets `np-api` (meaning "copied from the Nova Poshta catalog").
- No new index. "Last used" reads `carts` through the existing partial index `carts_customer_created`.

**`DeliveryPointInput`** (profile `PATCH` and checkout): `{warehouseRef}`, a GUID lowercased before validation and lookup, so uppercase is accepted. The profile `PATCH` also trims surrounding whitespace first; checkout does not trim. The profile `PATCH` also accepts `note` (ADR-0003 rules). Any other key → `400`. The server derives everything else from the catalog, so client-supplied names never need a charset rule.

**`NovaPoshtaPreference`** (output):

```text
{type:"branch"|"postomat", cityName, cityRef:string|null, warehouseNumber:string|null, warehouseRef:string|null,
 warehouseName:string|null, note:string|null, source:"manual"|"np-api", origin:"cabinet"|"checkout"|null}
```

**`CartDelivery`** (output, on carts): `{type, cityName, cityRef, warehouseNumber, warehouseRef, warehouseName}`. No note.

**Legacy preferences** (`source:"manual"`, `origin:null`, with or without `warehouseRef`): shown read-only in the cabinet with «Оберіть пункт із довідника, щоб використовувати його для замовлень». They are **never prefilled** at checkout (prefill requires `source:"np-api"`) and are replaced by the next `PATCH` or by the next signed-in checkout with a point.

### 6. Validation at write time

- **Rule.** `resolvePoint(warehouseRef)` must return a point. The stored values are the catalog's: `type` = `kind`, `cityRef`, `cityName`, `warehouseNumber` = `number`, `warehouseName` = `name`, `warehouseRef`.
- **Profile `PATCH deliveryPreference`.** Ref not in the catalog → `400 {error:"deliveryPreference.warehouseRef is not in the Nova Poshta catalog"}`. Snapshot unavailable → `503 {error:"Nova Poshta catalog is unavailable"}`. `null` clears every `np_*` column, including `np_origin` and `np_warehouse_name`.
- **Change detection.** A `PATCH` is a change when **any stored field differs**: type, city, number, Ref, name, note, source or origin. A re-save that only refreshes a renamed point, or «Зробити улюбленим» that only changes `origin`, is written and audited.
- **Checkout** (signed-in with `delivery`): Ref not in the catalog → `409 {error:"delivery_unavailable"}`; snapshot unavailable → `503 {error:"delivery_catalog_unavailable"}`. In both cases nothing is written. The UI keeps the cart lines and offers to choose another point or to check out without one.
- **Identity.** Two points are the same when their `warehouseRef`s are equal. Nothing else is compared.

### 7. Favourite, auto-remember and last used

- **Favourite** = the profile preference with `source:"np-api"`. `origin:"cabinet"`: set explicitly in the cabinet. `origin:"checkout"`: remembered from an order. A legacy preference (`source:"manual"`, `origin:null`) is not a favourite for prefill or for the checkout guard.
- **Last used** = the `CartDelivery` of the customer's newest bound cart that has one, by `created_at DESC, id DESC`. The carts table is the only source of truth. Under concurrent checkouts of one customer, the auto-remembered favourite reflects the last committed checkout; this rare difference is accepted.

| Situation | Prefill at checkout | Effect of a signed-in checkout with point P |
| --- | --- | --- |
| No favourite, or a legacy one (`source:"manual"`, with or without Ref) | Empty picker | Cart stores P; favourite := P with `origin:"checkout"` and `source:"np-api"` |
| Favourite F with `source:"np-api"`, `origin:"checkout"` | F | Cart stores P; favourite := P. No write and no audit when P has F's `warehouseRef`. |
| Favourite F with `source:"np-api"`, `origin:"cabinet"` | F | Cart stores P; **favourite unchanged**; P becomes last used through the cart |
| Checkout without a point | As above | Nothing changes |
| Anonymous checkout | Empty picker | Nothing stored (L2) |
| Cabinet `PATCH deliveryPreference:{warehouseRef}` | – | Favourite := the catalog point with `origin:"cabinet"` |
| Cabinet `PATCH deliveryPreference:null` | – | Everything cleared; prefill is **empty** until the next signed-in checkout with a point |
| «Зробити улюбленим» on an auto-remembered F | – | `PATCH {deliveryPreference:{warehouseRef: F.warehouseRef}}`; `origin` becomes `cabinet` |

- **Last, not first.** People move, or choose a one-off point for a first order; a customer who wants stability has the explicit favourite, which checkout never overwrites. Reversible (L4).
- **Prefill of a point that left the catalog.** The stored snapshot is shown; checkout then answers `409 delivery_unavailable` and the customer chooses another point.
- **Write** (in the checkout batch). Verified with `node:sqlite` (Node 22.23), rows changed: no row → 1; `np-api` same Ref with a changed name → 0; `np-api` other Ref → 1; legacy `manual` without Ref, origin `NULL` → 1; legacy `manual` **with the same Ref**, origin `NULL` → 1; legacy `manual` with the same Ref and origin `cabinet` → 1; `np-api` same Ref `checkout` → 0; `np-api` cabinet favourite → 0; profile row without a point → 1.

  Then `INSERT INTO customer_audit_events … SELECT … WHERE changes() > 0` with action `profile.delivery-remembered` and fields `["deliveryPreference"]` (names only). `audit()` in `customer-auth.js` is module-private, so `carts.js` prepares this statement itself (`id, customer_id, action, fields, created_at`); `customer-auth.js` is not changed. The cart insert, lines, upsert and audit are one D1 batch.

### 9. Retention, export, deletion and staff visibility

Migration 0024 adds nullable `carts.rcpt_last_name`/`rcpt_first_name`/`rcpt_middle_name` and `customer_profiles.last_name`/`first_name`/`middle_name` (additive, no backfill). New checkouts leave `rcpt_name` NULL. Carts created keep `rcpt_name` and are returned with null parts and `name` set to that value, never split by guessing. Prefill now comes from the profile parts. A legacy single-field `displayName` is kept but not used for prefill, so without stored parts the checkout name inputs stay empty. Account deletion clears all `rcpt_*` columns, and staff views are unchanged.

## Consequences

- **No Workers Paid dependency.** Delivery requests are dispatched before the recognition load and the D1 check, so they do at most one manifest parse (cached per isolate), one small JSON parse (≤ 132 KB) and one streamed range read; the expensive work runs in the sync script. Profile and checkout writes add one Ref-shard parse (≤ 117 KB) to requests that already use D1.
- **No upstream dependency at request time.** If Nova Poshta is down, nothing changes for customers; the catalog only gets older.
- **Staleness.** Points opened or closed since the last sync are missing or still listed. A closed point chosen from a stale catalog reaches the manager, who resolves it by hand. A missing snapshot (fresh environment, no bucket) disables the picker but never blocks checkout without a point.
- **Keyless dependency.** Keyless access is observed, not documented. If Nova Poshta enforces keys, syncs fail and the catalog stays at its last snapshot; a key can then be supplied through `NOVA_POSHTA_API_KEY` (a lead decision, since it needs a business account).
- **Credentials.** Automation needs an R2 write token in GitHub (L6). The local default needs a person with a token.
- **Discovered work** (reported to the orchestrator): no CSP or `Permissions-Policy`; no contacts or Telegram cabinet UI and no profile client (T6 builds only the delivery card); `docs/ARCHITECTURE.md` and ADR-0003 cited `migrations/0005` for the profile table, which is `0006`.

## Revisit triggers

- Nova Poshta rejects keyless requests (syncs fail): the lead decides on a business account and key.
- The lead answers L2–L7 or ADR-0007 Q1.
- The catalog gets older than 7 days in production more than once: automate (L6) or alert.
- A sync is refused by the 80% rule without a real reduction in Nova Poshta's network: tune the threshold or add the reference module's repeated-absence rule.
- The Kyiv postomat slice exceeds **1 MB gzipped**, picker time-to-list exceeds **3 s** on a mid-range phone, or a sync needs more than **1,000 uploads** (the Cloudflare API allows 1,200 requests per 5 minutes): split slices, add server-side paging, or upload through the R2 S3 API.
- R2 class B operations exceed 50% of the free tier: add an edge cache or a Cloudflare rate-limiting rule.
- A new pickup-point `CategoryOfWarehouse` appears (the allowlist excludes it until reviewed).
- A CSP or `Permissions-Policy` is introduced: keep `connect-src 'self'` and `geolocation=(self)`.
- Waybills, tariffs or tracking are requested: a new ADR (needs a key; `@weblabllc/delivery-core` is the leading library candidate).
